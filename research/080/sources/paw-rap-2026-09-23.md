# ProgramAsWeights, Rules as Programs, and the local compilers: recipe card (2026-09-23)

The PAW author is Yuntian Deng (University of Waterloo; GitHub `da03`), with Wentao Zhang, Liliana
Hotsko, Woojeong Kim, Pengyu Nie and Stuart Shieber. The GitHub API, repository files and the arXiv
API were read. Nothing was installed or run. Third-party numbers are **Reported** unless marked
**Reproduced**, which here means recomputed from their frozen prediction files, not rerun models.

## What each piece is

- **PAW (paper, Reported).** A 4B compiler trained on FuzzyBench (10M examples, released) emits
  adapters for a frozen interpreter. A 0.6B Qwen3 interpreter running PAW programs is reported to
  match direct prompting of Qwen3-32B at about 1/50 the inference memory, and 30 tok/s on an M3.
  It is the "compile once, call cheaply and offline" artifact form.
- **RAP.** Natural-language rules become functions that check a Codex agent's responses and tool
  calls through lifecycle hooks, running in a local daemon.
  - Precise conditions are Python; semantic conditions are PAW programs.
  - It **reports findings and never blocks.**
  - Every finding keeps the exact input and the rule revision. Findings from older revisions are
    marked for recheck.
  - Saved validation cases per rule, with a contrasting case, drive revision.
  - Operational failures (rule failed to load, compiler unavailable, inference error) are
    surfaced separately from `OK`: "a quiet inbox alone does not establish that monitoring is
    working."
  - Privacy: hosted compilation publishes the spec and its embedded examples as public,
    persistent programs.

## Evidence

**RAP frozen evaluation.** Author-constructed contrast pairs with labels fixed by construction;
specs and cases were co-designed. The positive class is any non-OK label. All values below are
**Reproduced** exactly from `outputs/frozen/*.jsonl` at head `901acfbbde`.

| System | Controlled (192 cases, 4 rules): P / R / macro-F1 / exact | External (160 cases, 8 purposive rules): P / R / macro-F1 / exact |
| --- | --- | --- |
| Rule-specific lexical code (bespoke, author-written) | 0.987 / 0.771 / 0.863 / 0.880 | **1.000 / 0.988 / 0.993 / 0.994** |
| PAW standard (`paw-4b-qwen3-0.6b`) | 0.804 / 0.854 / 0.831 / 0.823 | 0.821 / 0.863 / 0.840 / 0.838 |
| PAW finetuned (`paw-ft-bs48`, snapshot 20260530) | **0.923 / 1.000 / 0.961 / 0.958** | 0.949 / 0.938 / 0.946 / 0.944 |
| Qwen3-4B-Instruct-2507 judge (independently prompted, L40S) | 0.721 / 0.969 / 0.839 / 0.797 | 0.795 / 0.875 / 0.845 / 0.819 |

The paired analysis is post hoc on the controlled set and was not rerun here (Reported). With
5,000 cluster draws over contrast pairs, finetuned PAW minus the Qwen judge is +0.122 macro-F1
(95% [0.086, 0.159]) and +0.162 exact accuracy, with Holm-adjusted exact randomization
p = 4.2e-7. Against the lexical diagnostic, Holm p = .008. They chose pair-cluster randomization
over McNemar deliberately.

**Reading.**
- On lexically observable rules, bespoke exact code wins (external set, 0.993).
- Where lexical matching can't see the distinction (controlled set, recall 0.771), a fine-tuned
  0.6B compiled function beats a 4B prompted judge by a large, well-quantified margin.
- Standard PAW (no fine-tune) is no better than the 4B judge.
- Scope limits:
  - Eight purposive rules plus four controlled rules.
  - Synthetic events and co-designed specs.
  - Not a prevalence sample.
  - The lexical baseline is per-rule author code. Its win shows rule observability, not general
    superiority.

## Worthy? Yes, for three reasons

1. **ExoPO paper: RAP is the closest direct prior art, and it must be cited.** It is literally
   "instead of hoping your agent follows the rules, let the rules check your agent": exogenous,
   versioned rules outside the agent's weights. The positioning is clean:
   - RAP is detection. It reports and does not block, and its hooks are probed for fail-open
     behavior.
   - ExoPO is placement plus acceptance: which decisions leave the weights, who has authority
     over the act, and how a change is accepted.
   - For irreversible actions, a rule after the fact is detection, not prevention (AGENTS.md).
     A pre-effect gate must fail closed.
   - Scoop check: RAP does not claim a placement test or an acceptance protocol.
2. **Trainer: evidence for the artifact-form ladder, plus a runnable local path.**
   - Supported order: exact program → compiled function (fine-tuned, not standard) → model judge.
   - The new local `compiler` removes the off-box compile for Standard and Compact.
   - `paw-ft` can run fully local if its teacher is our own vLLM server (Qwen3-4B-Instruct-2507,
     Apache-2.0) and step 1 uses the local compiler. That needs a small first-party patch to its
     step 1.
3. **Evaluation hygiene worth adopting in `augustus-train`:**
   - frozen protocol versions with deviation notes;
   - sidecar manifests: output hash, git state, package versions, compiler snapshot;
   - contrast-pair cluster resampling;
   - Holm across declared comparators;
   - findings bound to rule revisions, with stale-finding detection;
   - operational failure never recorded as `OK`.

## What it changes for v4

- **M5 arms.**
  - Add PAW-standard (local compiler) and PAW-ft (local teacher plus local initial compile) on
    T2a–c.
  - Add an agent-synthesized program arm.
  - Same gate, same splits.
  - Every example is generated by local open weights. None is Jev output (D-d), and nothing
    leaves the box. D-e's hosted compile is then needed only if the local path fails on gfx1151.
- **GPU-only and precision parity.**
  - Run interpreters as exported PEFT adapters under transformers on the GPU.
  - Check parity against the SDK's llama.cpp GGUF runtime on a sample: precision is part of the
    model (Jev-Omni's 0.2 drift).
  - `paw-ft` needs a GPU budget of about 38 GiB. That is outside the 16 GiB CPU cgroup, so set
    it explicitly (GTT is not charged).
- **The skill's PAW section** moves from Hypothesis to "Reported, with a reproduced table",
  scoped to rule-check tasks. Two warnings go with it:
  - Hosted compilation publishes the spec and examples, so use the local compiler for anything
    sensitive.
  - Standard PAW is not better than a prompted 4B judge on these tasks; the fine-tune is what
    wins.
- **Composed programs.** RAP is a concrete instance of "exact Python checks plus compiled fuzzy
  checks" per rule. For the trainer, that is the composed decision program in which each
  sub-decision takes its cheapest adequate form.


## 2026-09-25: the PAW rungs are not reachable on an AMD envelope, and that is a finding

Checked while planning a second pinned image for M5, without cloning the repository or installing
anything. Three facts, each read from the published artifact:

- **`programasweights/compiler` is not a Python package.** One commit,
  `60138dce809e00365265c908b26ed8234a3684e4`, 2026-09-22, MIT, with a `requirements.txt` rather
  than a distribution. Its README states: *"Compilation requires Python 3.10+ and an NVIDIA GPU
  with BF16 support (Ampere or newer)."* Copying `compile.py` into an image without its
  requirements would not make A2a reachable.
- **The SDK's runtime is a source build behind a private index.** `programasweights` 0.4.10 on PyPI
  requires `llama-cpp-python>=0.3.0,<=0.3.19`, which has no binary wheel in that range on PyPI;
  0.3.19 is a source distribution that compiles llama.cpp. Its documented GPU wheels live on a
  CUDA index and a separate ROCm index, and the SDK's own install line adds
  `--extra-index-url https://pypi.programasweights.com/simple/`.
- tabputer is **gfx1151**, an AMD accelerator.

So A2a and A2b are unreachable here **in principle, not for want of a package**. That is a
different class of unreachable from "`setfit` is missing", and plan v4 §3.7 exists to keep the two
apart: one is an acquisition, the other is a portability limit of the artifact form itself.

**This is worth stating in the paper rather than only in a receipt.** The artifact-form ladder's
argument is that the cheapest adequate form should win. A rung that compiles only on one vendor's
accelerators, and whose inference runtime needs a source build plus a private package index, is a
rung most agents cannot climb whatever its accuracy. The measured RAP numbers above are unchanged
and remain the reason PAW is interesting; the reachability finding is about who can use it.

Nothing was installed, cloned, patched or compiled to establish this, and no allowlist entry was
requested. The compiler README is public and was read without the proxy.


## Correction, 2026-09-25: nothing in M5 is private, and the privacy note is about users

I gave hosted-compile privacy as a reason not to run A2a and A2b elsewhere. For M5 that reason is
wrong and is withdrawn.

M5's specs would embed examples drawn from the fit splits of **BANKING77 (CC BY 4.0), CLINC150
(CC BY 3.0) and CivilComments (CC0)**. Those rows are already public, and the spec text is our own
wording, which we publish anyway. Posting them to a hosted compiler as `public=True,
ephemeral=False` discloses nothing that is not already disclosed. There is no confidential input,
no customer traffic and no withheld label in a spec: the confirmation labels never enter one.

The privacy property is still worth recording, because it binds a **user of the trainer skill**
rather than this experiment. An agent that compiles a PAW program from a team's own rules embeds
that team's examples, and the hosted path makes them public and persistent. That is a real
constraint on the A2 rungs in deployment, and the skill has to say so where a recipe chooses a
compile route.

The honest objections to running A2a and A2b on another machine are therefore hardware, a second
environment to pin, and effort — not secrecy. Saying otherwise borrowed a concern from RAP's
context, where specs can carry real traffic, and applied it to an experiment made entirely of
public benchmark rows.

## Measured by us, 2026-09-25: the compiled program serves 17.8x faster than its own base

First figures in this record that are ours rather than reported. Colab L4, 22.5 GiB, driver
580.82.07, CUDA 13.0, `llama-cpp-python` 0.3.35 rebuilt with `-DGGML_CUDA=on` so
`llama_supports_gpu_offload()` is true, `n_gpu_layers=-1`, the same first 500 CivilComments
confirmation inputs both times.

| What was timed | Rows/s | Output |
| --- | ---: | --- |
| The bare Qwen3-0.6B interpreter, no compiled program | **1.29** | ~80 tokens of chat: *"I'm sorry, but I can't help with that…"* |
| The compiled `.paw` for T2c | **22.85** | **2 tokens**, mean 6.98 characters, `not toxic` / `toxic` |

**17.8x, and the mechanism is the token count rather than anything about the kernel.** The base
model is asked a question and answers at length because nothing tells it to stop; the compiled
program carries a prompt template and a LoRA trained to emit the label, and stops after two
tokens. Capping `max_tokens` at 8 changed the rate by 0.2%, which confirms the program was already
stopping on its own rather than being truncated.

This is PAW's "compile once, call cheaply and offline" claim, measured on hardware we can name,
and it holds. It also rescues the rung's feasibility: 78,845 confirmation rows project to about 58
minutes at this rate, against 17 hours for the uncompiled base.

Two cautions attached to our own number, since it is favourable. The 500 rows are one task's
inputs and CivilComments comments are short; T2a and T2b are unmeasured and their states differ.
And this is single-call inference with no batching, which is what the SDK's local path does — a
throughput figure, not a latency-under-load figure, and not comparable to a batched server like
`arbiter`'s.

The earlier measurement is kept rather than discarded. A CPU-only build of the same runtime
managed fewer than 1.18 rows/s on the bare interpreter before being stopped, which is the other
end of the envelope and is exactly what a recipe must tell an agent that has no GPU.

## 2026-09-25: two defects in the PAW-ft recipe, found by running it

Recorded because they are properties of the artifact form's tooling, which is what M5 measures,
and because both were found by executing the recipe rather than reading it.

- **Its teacher scheduler leaks.** `compile-by-training` creates all of its teacher calls at once
  and then waits with `asyncio.FIRST_COMPLETED`, which returns a task still queued on the
  semaphore and never collects it. The run stalls. The repair is in a recorded diff rather than a
  silent edit, and the throughput figure below came from a separate driver calling the recipe's
  own `one_teacher_call`, because the in-file repair still stalled.
- **It rejects a teacher response that is short by one.** A call is discarded unless it returns
  all eight requested examples, which a local 4B model frequently misses. That silently multiplies
  the number of calls needed, and it is invisible unless you count.

**And a measured cost.** With a local `Qwen3-4B-Instruct-2507` served through `transformers` at
concurrency 4 on an A100-40GB, the teacher produced **29 examples per minute**, linear from 8 to
136. The recipe asks for 4,800 examples per task, which is **2.8 hours per task and about 8 hours
for M5's three** — before the fine-tune starts. That is a wall-clock finding, not a memory one:
peak GPU was 23.3 GiB of 39.5.

The serving path matters and is separable from the recipe. `vllm` would not import on that VM —
its torch is CUDA 12.8 and `libcudart.so.13` is absent, the only published `nvidia-cuda-runtime-cu13`
being a stub — so the teacher ran through `transformers` instead. **Substituting the server is not
substituting the arm**, and it is named here so nobody infers it later. It is also the second time
today that a projection collapsed once the right configuration was measured: A2a's 17 hours became
58 minutes with a compiled program, and this figure is a property of an unbatched HTTP shim rather
than of the recipe.

The local route itself was clean and asserted rather than assumed: step 1 ran the pinned compiler
at commit `60138dce…` in 38.6–39.6 s at 8.0 GiB peak, made no HTTP request, and every established
socket during the run was loopback. **No step posted the spec.**

### The teacher cost was the serving path, twice over

The 29 examples per minute above is a property of an unbatched HTTP shim, not of the recipe, and
saying so was cheap while measuring it was not. Batched `model.generate` on the same A100-40GB,
batch 16, left-padded, one tokenizer batch and no server at all, ran at **315.6/min on a 200-example
probe and 347.6/min across the full 4,800**, at 7.5 GiB resident. That is about twelve times the
shim, and it moves one task's synthesis from 2.8 hours to roughly 14 minutes.

**Three projections in one day were properties of how something was served, not of the artifact.**
A2a's bare interpreter projected 17 hours and the compiled program took 58 minutes. R3a projected
7.6 hours at SetFit's default pair expansion and took 17 minutes under a declared pair budget.
A2b's teacher projected 8 hours through a shim and takes about 42 minutes batched. The pattern is
worth more than any of the three numbers: **a rung that looks too expensive to run is a claim about
the configuration measured, and it is usually wrong the first time.** None of the three was fixed
by reducing what the recipe asked for.

The 4,800 examples that run produced were discarded rather than kept, because they were synthesized
from a spec that has since been found to misdescribe its own labels. A cheap artifact built from
the wrong instructions is not a saving.
