# Release acceptance

Use only when the current user has authorized a release. Collection and local
checks alone do not authorize publishing or changing account settings.

- Record the candidate revision, development version, scope, and patch/minor
  rationale. Align skill/marketplace versions and release-facing README,
  changelog, citation metadata, Pages links, and notes. Preserve old notes.
- For research releases, complete the protocol's coverage ledger, inspect
  changed primary artifacts, and keep unknowns and unrun reproductions visible.
- Run `make check`; inspect the complete diff. Keep fresh behavioral outputs
  and independent acceptance findings. Structural lint is not semantic review.
  Honor requested reviewer models and preserve routing/identity limits. When
  redoing delegated work, map every original scope to independently re-derived
  evidence; do not relabel historical model output or repeat publication.
- Validate Claude packaging in isolation. Test the exact candidate/tag with a
  fresh configuration; inspect discovered skills and unexpected components.
  Test advertised Skills CLI discovery with `--list`; it is not an activation
  or production-use test. When the description or activation examples change,
  run the optional activation check (CONTRIBUTING) or record implicit
  activation as unmeasured. Do not modify normal user plugin settings.
- Build/check the rendered Pages output when release-facing content changes.
  Record whether browser layout/keyboard checks were needed and actually run.
- Push a scoped branch and PR; inspect CI and merge only the intended head.
  Check main again. Create a new tag; never move an existing published tag.
- Publish release notes with evidence limitations, then read back the release,
  tag target, latest-release status, and deployed Pages commit/content.
- Read back GitHub description, homepage, and topics against the current
  mission. A local README correction does not update the repository's About
  field. Change only authorized fields; do not alter account/security settings.
- When positioning changes, audit existing awesome-list/directory entries and
  submissions. Separate accepted entries, open requests, rejected requests, and
  crawler-managed pages. Recommend in-place corrections with each maintainer's
  contribution rules; do not duplicate submissions or reopen a scope rejection.
  An audit does not authorize third-party PRs, issues, or outreach. Record the
  current wording and next action rather than claiming listings updated.
- Leave a publication receipt linking checks and exact revisions. Historical
  pre-release audits remain historical; link the receipt rather than rewrite
  them as if deployment had already happened. Report a clean or explained tree.

Public availability, search indexing, implicit activation, and user benefit are
different claims. A successful release proves neither indexing nor growth.
